## 问   
什么东西是删除器我都不知道   

## 答
删除器（deleter）其实就是一个**“当 `shared_ptr` 的引用计数归零时，用来销毁它所管理对象的东西”**。默认情况下它就是一个普通的 `delete`，但你可以换成自己的逻辑。理解它之后，前面那段死锁描述就通了。

---

### 1. 默认删除器：就是 `delete`

```cpp
std::shared_ptr<int> p(new int(42));
```

当 `p` 的引用计数归零时，`shared_ptr` 会执行：

```cpp
delete 那个 int 指针;  // 这就是默认删除器
```

对 `make_shared` 创建的对象，默认删除器做的是调用对象的析构函数并释放控制块内存。

---

### 2. 为什么需要自定义删除器？

因为 `shared_ptr` 管理的“资源”不一定是用 `new` 分配的、也不一定该用 `delete` 释放。常见场景：

| 资源 | 默认 `delete` 的问题 | 需要自定义删除器 |
|---|---|---|
| `FILE*`（`fopen` 打开） | 不能用 `delete`，要用 `fclose` | ✅ |
| `malloc` 分配的内存 | 要用 `free` 而不是 `delete` | ✅ |
| `new[]` 数组 | 要用 `delete[]` 而不是 `delete` | ✅ |
| socket / 数据库连接 | 要 `close` / 归还连接池 | ✅ |
| 需要打日志、统计 | 释放前想记录一下 | ✅ |

---

### 3. 自定义删除器长什么样

删除器可以是**函数指针、lambda、函数对象**，只要能用 `(指针)` 调用即可。

**函数指针**：
```cpp
void close_file(FILE* f) {
    if (f) fclose(f);
}

std::shared_ptr<FILE> fp(fopen("a.txt", "r"), close_file);
// 计数归零时调用 close_file(fp.get())，而不是 delete
```

**lambda**：
```cpp
std::shared_ptr<FILE> fp(
    fopen("a.txt", "r"),
    [](FILE* f) { if (f) fclose(f); }
);
```

**函数对象**：
```cpp
struct FreeDeleter {
    void operator()(void* p) const { free(p); }
};
std::shared_ptr<void> buf(malloc(1024), FreeDeleter{});
```

---

### 4. 删除器什么时候被调用？

**只在引用计数归零的那一刻**，由最后一个释放 `shared_ptr` 的线程调用。调用发生在 `shared_ptr` 的析构、`reset()`、或赋值覆盖旧值时。

```cpp
{
    std::shared_ptr<FILE> fp(fopen("a.txt", "r"), [](FILE* f){
        std::cout << "关闭文件\n";
        fclose(f);
    });
    // 这里引用计数是 1
} // fp 离开作用域，计数归零 → 调用 lambda → 打印"关闭文件" → fclose
```

---

### 5. 回到前面的死锁：删除器就是“计数归零时要执行的用户代码”

前面说的“内部锁自死锁”，逻辑是这样的：

1. `shared_ptr` 在修改引用计数时，会持有**一把内部锁**（保护计数的原子性）。
2. 某次操作导致计数归零，`shared_ptr` 需要调用**删除器**来销毁对象。
3. 如果这个删除器的代码里，**又去操作了同一个 `shared_ptr` 的控制块**（比如再次赋值、reset），就会尝试获取**同一把内部锁**。
4. 锁已经被自己拿着 → 自死锁。

```cpp
// 概念示意（不是真实标准库代码）
std::shared_ptr<X> p(new X, [](X* x){
    // 这是删除器，计数归零时执行
    // 如果这里又对 p 做了赋值/reset，就会再次锁内部锁
    delete x;
});

// 内部实现大致是：
lock(internal_mutex);
if (--refcount == 0) {
    deleter(ptr);   // ← 删除器在这里被调用，锁还拿着
}
unlock(internal_mutex);
```

libc++ 的修复就是把 `deleter(ptr)` 挪到 `unlock` 之后执行，这样删除器即使再碰同一个控制块也不会死锁。

**所以“删除器行为不端”的意思是：删除器本来只该负责销毁资源，但它在被调用时又去碰了正在处理的那个 `shared_ptr`，导致重入内部锁。**

---

### 6. 补充：场景二里其实不是删除器

前面第二个死锁场景（MongoDB 那个）用的是 `weak_ptr::lock()`，里面**没有自定义删除器**，它触发的是**对象自己的析构函数**。但本质相同：

- 删除器 = 计数归零时执行的“销毁逻辑”
- 析构函数 = 对象被销毁时执行的“清理逻辑”

两者都是**在引用计数归零的路径上被调用的用户代码**，如果这段用户代码去抢一把当前已经被持有的锁（不管是 `shared_ptr` 内部锁还是你的业务锁），就会死锁。

---

### 一句话总结

> **删除器 = 你告诉 `shared_ptr`：“计数归零时，请用这段代码来销毁我的资源。”** 默认是 `delete`，你可以换成 `fclose`、`free`、lambda 等。它是在 `shared_ptr` 内部释放资源的路径上被调用的用户代码，所以如果它里面又去操作同一个 `shared_ptr` 或抢同一把锁，就会引发前面说的死锁。
